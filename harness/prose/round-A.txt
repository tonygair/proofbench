SPARK RULES THAT COST THIS SHOP REAL ITERATIONS. Each one below has failed a

1. AN "out" PARAMETER MUST BE INITIALISED ON EVERY PATH, AND FLOW ANALYSIS
   WILL NOT TAKE A LOOP'S WORD FOR IT.
   This is the single most expensive mistake on this lane. SPARK's flow
   analysis is not the prover; it does not reason about ranges. A loop that
   plainly writes every element of an "out" array still leaves flow analysis
   saying the array "might not be initialized", because flow analysis does not
   know the loop covers the whole range.
   The fix is one statement, placed BEFORE the loop, that initialises the whole
   object at once:
        Result := (others => <some legal value of the element type>);
   Write it even when the loop that follows overwrites every element. It costs
   one line and it is the difference between a proof and a failure. The same
   applies to an "out" scalar: assign it on every path, including paths you
   believe unreachable.
   Ada has no way to say "the loop covers it". Initialise the whole thing.

2. A LOOP INVARIANT MUST BE INDUCTIVE, NOT MERELY TRUE.
   The prover proves your invariant holds on entry to the first iteration, and
   that IF it holds at the top of an iteration THEN it holds at the top of the
   next. It then has the invariant, and the negated exit condition, and nothing
   else, to prove your Post. So:
     - The invariant must speak about EVERY index processed so far, not about
       the current one and not about one or two remembered values. An invariant
       of the shape "(for all J in <first> .. <current> => <the property>)" is
       usually what is needed; an invariant naming only the latest element is
       the classic failure and proves nothing on exit.
     - On exit, the invariant plus "the loop ran to the end" must IMPLY the
       whole Post. Read your Post, then ask whether your invariant delivers it
       at the last index. If it does not, the invariant is too weak.
     - Anything the loop leaves unchanged but the Post talks about must be
       stated in the invariant too. The prover forgets everything not carried
       by the invariant. Use X'Loop_Entry to refer to a value as it was before
       the loop.
   Placement: a pragma Loop_Invariant must sit among the statements of the loop
   body, at the top level of that body — not nested inside an if, and not in a
   declarative part. Immediately after the statements that establish it is the
   usual place.

3. WRITE ADA, NOT PSEUDO-ADA. These exact inventions have been emitted here:
     - "implies" is NOT an Ada operator. Write (if X then Y).
     - "Pre'Class" / "Post'Class" are only legal on a primitive of a tagged
       type. On a plain subprogram write Pre and Post.
     - Do not mix "and" with "and then", or "or" with "or else", in one
       expression without parentheses: GNAT rejects it as mixed logical
       operators. Parenthesise, or pick one form.
     - Quantifiers are (for all J in Range => Expr) and (for some J in Range
       => Expr). The arrow is required.
     - 'Result is legal only inside a function's Post.
     - Array attributes are A'First, A'Last, A'Range, A'Length. There is no
       A'Size for the element count.

4. EVERY RUN-TIME CHECK MUST BE PROVABLE, AND THE TYPES HERE ARE BOUNDED.
   The subtypes in the preamble have real bounds, so overflow and range checks
   are genuine obligations, not formalities. An intermediate value that leaves
   its subtype's range is an unproved check even when the final answer would
   have been in range.
     - Before an arithmetic operation whose operands you cannot bound from the
       declared subtypes alone, state the bound the prover needs — as a loop
       invariant if it is carried across iterations, as a pragma Assert if it
       is local.
     - If the specification's Pre already bounds an input, you may rely on it;
       if it does not, you must derive the bound from the subtype declarations
       in the preamble and say so.
     - Indexing: prove the index is in A'Range. Inside "for I in A'Range" this
       is free for A, but NOT for a second array unless its bounds are tied to
       A's by the Pre. Read the Pre and use what it gives you.
     - Division and mod: the divisor must be provably non-zero.

5. USE THE SPECIFICATION AS THE INSTRUCTION.
   The Post is the whole of what you must achieve — no more and no less. Do not
   implement a behaviour the Post does not ask for, and do not weaken what it
   does ask for. Where the Post is a conjunction, satisfy every conjunct; an
   invariant that establishes one conjunct and forgets another is the second
   most common failure here.

6. SIMPLEST BODY THAT DISCHARGES.

   function helper over a procedure helper. Do not add annotations that carry
   no proof obligation you need — they cost prover time and can confuse the
