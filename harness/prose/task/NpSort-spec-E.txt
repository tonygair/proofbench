1. AN "out" PARAMETER MUST BE INITIALISED ON EVERY PATH, AND FLOW ANALYSIS
   WILL NOT TAKE A LOOP'S WORD FOR IT.
   SPARK's flow analysis is not the prover; it does not reason about ranges.
   A loop that plainly writes every element of an "out" array still leaves flow
   analysis saying the array "might not be initialized".
   The fix is one statement, placed BEFORE the loop, initialising the whole
   object at once:
        Result := (others => <a LITERAL constant of the element type>);
   Write it even when the loop that follows overwrites every element. For an
   "out" scalar, assign it on every path, including paths you believe
   unreachable.

   ★ THE INITIALISER MUST BE A LITERAL — 0, False, and so on. Do NOT read a
   value out of another array to seed it. "Result := (others => A (A'First));"
   looks harmless and is an unprovable index check: unless the Pre says
   A'Length > 0, the array may be empty and A'First is then not a valid index.
   Read the Pre. If it does not guarantee a non-empty array, index nothing
   before the loop.

2. ★ THE LOOP INVARIANT GOES AT THE **END** OF THE LOOP BODY, AFTER THE WORK.
   This is now the most expensive mistake on this lane. A pragma
   Loop_Invariant is checked WHERE IT STANDS. Put it FIRST, before the
   statement that does the iteration's work, and at that moment the current
   index has not been written yet — so an invariant claiming anything about
   the current index is false, and an invariant that dodges the problem by
   claiming nothing carries nothing to the postcondition. Both were emitted
   here and both failed.

   Write the loop in this shape, always:

        for I in <the range> loop
           <the statements that do this iteration's work>
           pragma Loop_Invariant (<what is true of everything done so far>);
        end loop;

   And "what is true of everything done so far" means a quantified statement
   over the whole processed prefix, INCLUDING the current index:

        pragma Loop_Invariant
          (for all J in <the first index> .. I => <the property the Post
                                                   asserts about index J>);

   Read the Post. Whatever the Post asserts for every index, your invariant
   asserts for every index up to and including I. On the last iteration those
   two statements coincide, and that is how the Post gets proved. An invariant
   that speaks only about the current element, or only about the element
   before it, proves nothing on exit.

   If the Post is a conjunction, carry EVERY conjunct in the invariant. An
   invariant that establishes one conjunct and forgets another is the second
   most common failure here.

3. ★ 'Loop_Entry IS FOR FRAMING WHAT DID **NOT** CHANGE. IT CAN NEVER STATE
   PROGRESS.
   X'Loop_Entry is the value X had BEFORE the loop began. Writing
   "Result'Loop_Entry (I) = 0" says something about the pre-loop value; it says
   nothing whatever about the work the loop has done, so it carries nothing to
   the Post. Every invariant of that shape emitted here has failed.
   Use 'Loop_Entry ONLY to say that something the Post mentions is unchanged by
   the loop. To say what the loop has ACHIEVED, quantify over the processed
   prefix as in rule 2 — with the plain name, not 'Loop_Entry.

4. ★ A pragma Loop_Invariant MUST STAND IMMEDIATELY AMONG THE LOOP'S OWN
   STATEMENTS.
   Not in a declarative part. Not before the "loop" keyword. Not nested inside
   an if or a case inside the loop. GNAT rejects any of those outright with
   "must appear immediately within the statements of a loop". If the work is
   done inside an if, close the if first, then write the invariant after it at
   the top level of the loop body.

5. ★ A QUANTIFIED VARIABLE IS NOT ITS OWN BOUND.
   "(for all J in A'First .. J => ...)" is illegal — J is not visible in its
   own range. The bound is the LOOP COUNTER; the quantified variable is a
   different name. Write "(for all J in A'First .. I => ...)" where I is the
   loop counter and J is the quantified variable. Never let the same
   identifier appear as both.

6. ★ INDEX FROM THE ARRAY'S OWN BOUNDS, NEVER FROM A LITERAL.
   These arrays are unconstrained; A'First is NOT guaranteed to be 0. Writing a
   slice or a range as "0 .. I" produces a range check that cannot be proved
   and often cannot even be justified. Always write A'First, A'Last, A'Range,
   or the loop counter. The same goes for Result: use Result'First, and note
   the Pre usually ties Result's bounds to A's — read it and use it.

7. ★ YOUR ARRAY TYPES HAVE NO ARITHMETIC OR LOGICAL OPERATORS, AND YOU CANNOT
   COMPARE A SLICE TO AN AGGREGATE.
   There is no "and", "or", "xor", "+" or "*" defined for a user-defined array
   type here, so "A (A'First .. I) and B (A'First .. I)" does not compile.
   Likewise "Result (A'First .. I) = (others => 0)" does not compile — an
   "others" aggregate has no bounds in that position.
   Say all of it element-wise with a quantifier instead:
        (for all J in A'First .. I => Result (J) = <expression in A (J), B (J)>)
   Element-wise quantification is the only form that both compiles and proves.

7b. ★ A QUANTIFIED EXPRESSION IS A BOOLEAN. IT DOES NOT RETURN A VALUE.
   "(for some J in A'Range => A (J))" is not the largest element, not any
   element, and not a number of any kind - it is a type error, and GNAT says
   "expected type Standard.Boolean". This was emitted three times on this lane.
   To say that Result is one of the elements, put the equality INSIDE the
   quantifier, where it belongs:

9. NESTED LOOPS: THE INNER INVARIANT HAS **TWO** PARTS, NOT ONE.
==========================================================================
   This is the most expensive mistake on the matrix lane. It has been emitted
   here on EVERY matrix task so far and GNATprove rejected every one with
   "loop invariant might fail in first iteration".

   In a nested loop the inner invariant must describe EXACTLY what has been
   written at that moment, which is:
     (a) every EARLIER outer row, COMPLETELY; and
     (b) the CURRENT outer row, only UP TO the current inner index.

   Claiming the whole inner range for the current row - "for all rows up to and
   including I, for all columns" - is FALSE IN THE FIRST INNER ITERATION,
   because the current row has had only one element written.

   Write the two parts, always, in this shape:

        for I in A'Range (1) loop
           for J in A'Range (2) loop
              Result (J, I) := A (I, J);
              pragma Loop_Invariant
                ((for all K in A'First (1) .. I - 1 =>          -- (a) EARLIER rows, whole
                    (for all L in A'Range (2) =>
                       Result (L, K) = A (K, L)))
                 and then
                 (for all L in A'First (2) .. J =>              -- (b) CURRENT row, so far
                    Result (L, I) = A (I, L)));
           end loop;
           pragma Loop_Invariant                                -- outer: rows <= I whole
             (for all K in A'First (1) .. I =>
                (for all L in A'Range (2) =>
                   Result (L, K) = A (K, L)));
        end loop;

   The outer loop carries its OWN invariant, at the END of the outer body,
   saying every row up to and including I is complete. Without it, part (a) has
   nothing to stand on in the next outer pass.

   The same two-part shape applies whenever the written element depends on both
   indices, including masking tasks that write 0 in one region and copy in the
   other: state BOTH regions in BOTH parts.

10. AN ARITHMETIC POST NEEDS ITS RANGE CARRIED IN THE INVARIANT.
   If the Post multiplies or accumulates ("Result (I) = Result (I - 1) * A (I)"),
   the prover must know the running value is still in range BEFORE it multiplies
   again, or it answers "range check might fail, cannot prove lower bound".
   Add to the invariant an explicit bound on every element written so far, using
   the constants the preamble gives you, e.g.
        (for all K in A'First .. I => Result (K) in -Max_Product .. Max_Product)
   State the bound for BOTH signs. Read the preamble for the constant that
   bounds the accumulation; it is there because you need it.
